# i18n — Internationalization System

> **Status:** Active — EN/ES client-side switcher (no URL routing)
> **Added:** 2026-05-09 (between Phase 2 and Phase 3 of landing-v1)
> **Part of:** [[Architecture]]

## Overview

All site copy is centralized in a single TypeScript file. Language switching happens
client-side via DOM manipulation — no page reload, no URL change.

Default language rendered at build time: **Spanish (es)**.

## File Structure

```
src/
├── i18n/
│   └── translations.ts         # Master translations object (ES + EN) — as const
└── utils/
    └── i18n.ts                 # DIP abstraction: getLang(), useTranslations()
src/components/
    └── LanguageSwitcher.astro  # EN/ES toggle button
src/layouts/
    └── BaseLayout.astro        # Anti-flash script injected in <head>
```

## translations.ts — Structure

Top-level keys map to site sections. Each section contains `es` and `en` sub-objects:

```ts
export const translations = {
  nav:            { es: {...}, en: {...} },
  hero:           { es: {...}, en: {...} },
  stats:          { es: [...], en: [...] },
  educationStack: { es: {...}, en: {...} },
  services:       { es: {...}, en: {...} },
  testimonials:   { es: {...}, en: {...} },
  footer:         { es: {...}, en: {...} },
} as const

export type Lang = 'es' | 'en'
```

## utils/i18n.ts — API

```ts
getLang(): Lang                 // reads localStorage('lang'), fallback: 'es'
useTranslations(section, lang)  // returns typed translations[section][lang]
```

Components import `useTranslations` — never `translations` directly (DIP).

## data-i18n Convention

Every text element that must swap on language change carries a `data-i18n` attribute.

### Simple keys
```html
<span data-i18n="hero.tagline">THE NEON ARCHITECT</span>
```

### Array keys (zero-indexed)
```html
<p data-i18n="stats.0.label">Velocidad de desarrollo</p>
<p data-i18n="stats.1.label">Reducción de errores</p>
```

The switcher script resolves keys by inserting the target lang in position 1:
`"stats.0.label"` → `translations.stats.en[0].label`

### What NOT to translate
- Technology names (React, Python, FastAPI, LangChain…) — same in both languages
- Stack category tokens used in CSS (`data-category="backend"`) — not visible text

## Language Switch Flow

### Initialization (`initSwitcher`, on `DOMContentLoaded`)

1. Resolve the current language: `localStorage.lang` if valid, otherwise
   `resolveBrowserLang(navigator.language)`
2. **Persist the resolved value** — including when it came from the browser locale
3. Apply it to the DOM if it is not the build-time default (`es`)
4. Bind the click handler

### On click

1. Read the language **from `document.documentElement.lang`** — what is actually on screen
2. Compute the opposite language, write it to `localStorage`
3. Query all `[data-i18n]` elements; for each, resolve the key and replace `textContent`
   (never `innerHTML` — XSS safe)
4. Set `document.documentElement.lang`, dispatch `language-changed`
5. Update the button label to show the language you would switch *to*

## Anti-Flash Script

Injected inline in `<head>` of `BaseLayout.astro` via `is:inline`. Runs before first paint:
reads `localStorage.lang` and sets `<html lang="en">` if needed, preventing a flash
of Spanish text on returning English-language visitors.

## Fixed: the first switcher click was a no-op

> **Status:** Fixed — **Date:** 2026-08-21 — **Severity:** Medium

**Symptom.** For any visitor arriving with a non-Spanish browser, the first click on the
EN/ES button did nothing visible. The second click worked.

**Root cause.** Two halves of the component disagreed about where the current language
lived. `initSwitcher` resolved it from `navigator.language` and applied it to the DOM
**without persisting it**. The click handler then read `localStorage.getItem('lang')` —
still empty — fell back to `'es'`, computed `'en'` as "the next language", and re-applied
the language already on screen. Nothing changed, and nothing errored.

Spanish-browser visitors never saw it: for them the resolved language *was* the fallback,
so the two sources happened to agree.

**Fix.** `initSwitcher` now writes the resolved language to `localStorage` even when it
came from the browser locale, and the toggle derives the current language from
`document.documentElement.lang` rather than from storage. State has one reader and one
writer per source.

**Prevention.** Covered by `tests/e2e/i18n-and-contact.spec.ts` — "one click switches the
copy and the html lang attribute" and "two clicks return to the original language". A unit
test could not have caught it: the defect lived in the disagreement between two runtime
state sources, not in either function alone. See [[testing-strategy]].

## Gotchas

- **A brief `lang`/copy mismatch is inherent to this design, not a bug.** The anti-flash
  script sets `<html lang>` before first paint; the copy swap runs on `DOMContentLoaded`.
  Between the two, an English visitor has `lang="en"` on a document still showing Spanish
  text. Closing that window requires rendering per language, which means a URL per
  language — explicitly out of scope for v1 (no URL routing). Anything asserting on both
  at once must wait for the switcher to have run.

- `white-space: pre-line` required on hero subheadline — the EN/ES strings use `\n`
  for line breaks; `textContent` preserves `\n` but only CSS renders it as a line break.
- Special characters (`›`, `©`, `—`) stored as Unicode directly in `translations.ts`,
  not as HTML entities — `textContent` does not parse HTML entities.
- Stack category labels (`backend`, `ai`, `frontend`, `infra`) are CSS tokens, not
  translatable text — do not add `data-i18n` to `data-category` attributes.
