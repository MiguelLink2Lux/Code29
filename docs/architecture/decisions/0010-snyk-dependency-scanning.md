# ADR 0010 — Snyk scans dependencies for known vulnerabilities, outside the PR pipeline

- **Status:** Accepted
- **Date:** 2026-08-24
- **Deciders:** Miguel Navarro Mantas
- **Relates to:** [[0004-backend-deploy-provider]], [[testing-strategy]]

> **What this ADR is not.** It does not add a gate to `.github/workflows/ci.yml`. Snyk is
> connected through its own web integration against the GitHub repository, so it produces no
> GitHub check and **cannot block a merge**. That limitation is deliberate for now and stated
> in Consequences rather than hidden.

## Context and Problem Statement

`.github/workflows/ci.yml` answers whether the code we wrote behaves: lint, unit tests, build,
emitted-runtime and build-artifact assertions, end-to-end, `ruff`, `pytest`. It says nothing
about the code we did **not** write, which is most of what ships.

The exposure is not hypothetical and it is not small. The frontend pulls Astro, Vue and their
transitive trees through npm; the backend pins a resolved `requirements.txt` generated by
`backend/scripts/gen-requirements.sh` and deployed to Vercel as a serverless function. A
vulnerability disclosed in any of those packages after the pull request merged is invisible to
a pipeline that only runs on pull requests: nothing re-examines a dependency that was already
green when it landed.

Two properties make this worse here than in a long-lived service. The project is **public**, so
its dependency manifests are readable by anyone. And deployment is automatic — a merge to
`main` publishes production on both Vercel projects — so the window between "a vulnerable
package is in the lockfile" and "it is serving traffic" is a merge, not a release cycle.

So: something has to watch the dependency trees, and it has to keep watching after the merge.

## Decision Drivers

- **Coverage of both ecosystems.** npm and pip, or it only solves half the problem.
- **It must outlive the pull request.** A gate that runs only on PRs cannot see a disclosure
  that happens later, which is the common case.
- **Zero pipeline cost.** The CI run is currently ~1m20s. A scan that adds minutes to every
  push is a scan that gets disabled.
- **No new secret in the repository.** A `SNYK_TOKEN` in GitHub Actions is one more credential
  to rotate and leak, on a public repository.
- **Honest reporting.** Whatever is adopted must be describable exactly; a security control
  that is overstated is worse than none, because it stops anyone looking.

## Considered Options

1. **Snyk via its web/GitHub integration** — connect the repository from the Snyk side; Snyk
   imports the manifests and scans them.
2. **Snyk as a CI step** (`snyk/actions`) — a real GitHub check that can fail the build.
3. **GitHub Dependabot alerts** — native, free, no third party.
4. **Nothing** — accept the exposure for a portfolio site.

## Decision Outcome

**Option 1: Snyk connected through its web integration, scanning dependencies only.**

Concretely, and this is the whole of it:

| Property | Value |
|---|---|
| Connected via | Snyk web integration against the GitHub repository — **no workflow, no `SNYK_TOKEN`** |
| Scans | Dependency manifests only — npm (frontend) and pip (backend) |
| Snyk Code (SAST on our own source) | **Not enabled** |
| Automatic fix pull requests | **Not enabled** |
| Continuous re-scan | **Not configured** — treat results as a snapshot from the last import, not a live monitor |
| Blocks a merge | **No** — it produces no GitHub check |

Option 2 was rejected for now on the secret and the pipeline-time drivers, and because a
failing-build gate on a solo project with a delivery deadline is a gate that gets bypassed the
first time it is inconvenient — which teaches exactly the wrong lesson about gates. It remains
the obvious upgrade path.

Option 3 was not rejected on merit and is not exclusive with this one; Snyk was chosen because
its severity reasoning and remediation advice are more actionable than a bare alert, and
because it is the tool already in use elsewhere by the author.

Option 4 was rejected: the repository is public and deploys on merge.

## Consequences

**What this buys.** Known vulnerabilities in the two dependency trees are surfaced with a
severity and a remediation path, for an ecosystem coverage no gate in `ci.yml` provides.

**What it does not buy, stated plainly:**

- **It cannot stop a merge.** There is no GitHub check, so a pull request with a vulnerable
  dependency is as green as any other. The verification is *beside* the pipeline, not in it.
- **It does not watch our own code.** Snyk Code is off; SAST on `src/` and `backend/app/` is
  not covered by this decision. The security properties of our own code are asserted by tests
  instead — the SSRF guard (`test_url_guard`, 64 cases), the transcript isolation of the
  generation model (`test_grounded_generator`), Turnstile failing closed (`test_turnstile`).
- **It does not fix anything by itself.** With fix pull requests off, remediation is manual:
  read the finding, bump the package, regenerate `backend/requirements.txt` through
  `backend/scripts/gen-requirements.sh` — never by hand — and let the normal pipeline verify it.
- **Findings are a snapshot.** Without continuous monitoring configured, "no findings" means
  "none at the last import", not "none today".

**Reproducibility caveat.** Because the configuration lives in Snyk's dashboard rather than in
the repository, this ADR is the only record of it. A change made in that dashboard and not
reflected here makes this document wrong, and nothing in CI will notice. Treat the table above
as the contract: if the dashboard stops matching it, update this ADR in the same change.

## Verification status

Verified on 2026-08-24 by inspecting the repository: `.github/workflows/` contains only
`ci.yml`, whose jobs are `Frontend` and `Backend`; `grep -ri snyk` returns nothing in
`package.json`, `backend/pyproject.toml` or the workflows; the check runs reported on `main`
are `Frontend` and `Backend` only. All of which is consistent with — and is the evidence for —
"connected outside the repository, produces no check".

## Next step, when the delivery pressure is off

Promote to option 2: add a `snyk` job to `ci.yml`, and pair it with branch protection on `main`
so a failing scan actually blocks. That single change converts this from a report into a gate.
