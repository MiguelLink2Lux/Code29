# ADR 0004 — Deploy the FastAPI backend on Vercel as a second project

- **Status:** Accepted
- **Date:** 2026-08-21
- **Deciders:** Miguel Navarro Mantas

## Context and Problem Statement

The Phase 2 backend ([[0002-fastapi-as-backend-framework]]) lives in the same repository as
the Astro frontend ([[0001-backend-repo-structure]]) but had no deployment target: the ADR
index carried an explicit "deferred — deployment provider not yet decided" note, and
`tech-stack-decision` still guessed at Render/Railway. Getting `/api/v1/health` reachable in
production requires picking a provider and a project topology.

Two constraints shaped the decision:

1. **The backend cannot share the frontend's Vercel project.** The Astro frontend uses the
   `@astrojs/vercel` adapter v7, which emits the Build Output API into `.vercel/output`.
   A build that produces Build Output API takes over the deployment shape entirely, so
   Vercel's zero-config discovery of `api/` functions is suppressed. A Python function
   dropped into the frontend project would simply never be routed.
2. **Vercel does not read `pyproject.toml` or `uv`.** The Python runtime installs from a
   plain `requirements.txt`, while the project's canonical manifest is `pyproject.toml` +
   `uv.lock`.

## Decision Drivers

- One provider and one dashboard for the whole TFM — minimize operational surface.
- Deploy isolation: the backend must not be able to break the landing page's build.
- No new toolchain (no container registry, no Dockerfile) for a scaffolding-stage API.
- Keep `pyproject.toml` as the single canonical dependency manifest.

## Considered Options

1. **Vercel, as a second project with Root Directory `backend/`.**
2. **Google Cloud Run** — container deploy, scales to zero, keeps a real process alive per
   instance, and is the natural home for Genkit/Gemini workloads in Phase 3.
3. **Render** — simple Python service deploys, but the free tier sleeps the service, so the
   first request after idling pays a multi-second wake-up.
4. **Fly.io** — container deploy close to the user, persistent processes.
5. **Same Vercel project as the frontend** — ruled out on technical grounds by constraint (1)
   above, not by preference.

## Decision Outcome

Chosen option: **Vercel, as a second, independent Vercel project whose Root Directory is
`backend/`**.

The decisive driver was operational simplicity rather than runtime fit: a single provider and
a single dashboard for the entire TFM. Cloud Run is the better runtime match on the merits —
a persistent container, no cold start per request, and the environment Genkit/Gemini expects —
and it was rejected knowingly, accepting the consequences below.

Implementation shape:

- `backend/vercel.json` — a catch-all rewrite `"/(.*)" → "/api/index"`, so every path reaches
  the single function.
- `backend/api/index.py` — logic-free entrypoint doing `from app.main import app`. Local
  uvicorn, the test suite and the deployed function therefore serve the *same* object built by
  the `create_app()` factory.
- `backend/requirements.txt` — generated, never hand-edited.

### Consequences

- **Bad — FastAPI runs as a serverless function.** There is no persistent process: no
  in-process cache, no background tasks that outlive a response, no warm connection pool, and
  a cold start on the first request after idling. This is a real regression against a
  container host, accepted as the price of the single-provider setup.
- **Bad — a second dependency manifest exists.** `backend/requirements.txt` duplicates what
  `pyproject.toml` already declares, purely because Vercel cannot read `pyproject.toml`/uv.
  Mitigation: it is generated by `backend/scripts/gen-requirements.sh` (`uv export --no-dev
  --no-hashes --no-emit-project`), carries a "GENERATED FILE — do not edit by hand" header,
  and `backend/tests/test_requirements_manifest.py` fails the suite when the two manifests
  drift. `pyproject.toml` remains canonical; the generated file is an artifact of the host.
- **Bad — open risk for Phase 3.** The Genkit dependency tree pulls ~97 packages, including
  `anthropic`, `openai` and a full OpenTelemetry stack. That may exceed Vercel's serverless
  bundle size limit, and OpenTelemetry tracing fits a short-lived function poorly (spans must
  flush before the process freezes). If either problem materializes the backend moves to a
  container host — most likely Cloud Run — and `backend/vercel.json` plus `backend/api/index.py`
  become throwaway. The migration is additive: `create_app()` is host-agnostic.
- **Good — deploy isolation is structural.** The two projects build independently; the backend
  project can be created, broken or deleted without touching the landing page. It also
  sidesteps the adapter/`api/` incompatibility instead of fighting it.
- **Good — no new toolchain.** No Dockerfile, no registry, no separate CI provider.
- **Neutral — CORS stays explicit.** `CORS_ORIGINS` may never be `*`: the validator in
  `backend/app/core/config.py` raises on boot if a wildcard is present, so a misconfigured
  environment fails the deploy instead of shipping an open policy. Production must list the
  frontend's real origin.
- **Neutral — the frontend must be deployed from Git, never with `vercel --prebuilt`.**
  With a local Node version other than 20, the `@astrojs/vercel` v7 adapter bakes
  `"runtime": "nodejs18.x"` into `.vercel/output/functions/_render.func/.vc-config.json`, and
  Vercel has rejected Node 18 on new deployments since 2025-09-01. Building on Vercel makes
  the local Node version irrelevant; `.nvmrc` and `engines` pin 20 for local work.
